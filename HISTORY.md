## [0.4.4] - 2026-07-12

- **Experimental parallel cycle dispatch (#143).** Final slice of the cycling-mode epic (#145): `/iflow-cycle parallel:<n>` may run **provably independent** issues concurrently when the harness supports background execution — the sequential cycle remains the default and is never weakened to enable it. Only issues in `agent queue`'s `independent` set (no dependency relation to any other queue member) qualify; each runs in its own `git worktree`; **merges are serialized** by the coordinating session (rebase/retry on refusal); and shared files — chiefly `HISTORY.md` — are written **only by the coordinator in merge order**, never concurrently. If background execution can't be confirmed, the skill refuses `parallel:<n>` and runs sequentially. A new `parallel-cycle.md` design note (scaffolded with the standard cycle surface) records the constraints and per-harness notes, since editor capabilities move fast. Cross-repo parallel cycles remain out of scope.

- **Cycle resumability + failure policy (#142).** Stage 2 of the cycling-mode epic (#145) makes `/iflow-cycle` survivable. The cycle now writes a durable `cycle_status.md` (the confirmed queue as a checklist, the `onfail` policy, timestamps, per-issue outcomes) under `01-current-issues/`, updated as the loop runs and archived to `03-solved-issues/` when it finishes — so an interrupted run is never lost. **`/iflow-cycle resume`** picks up the remaining issues, re-verifying each is still open/unblocked via `agent queue` (state can move while paused) and **without** re-asking the original consolidated confirm for unchanged items. A **failure policy** token selects behaviour on a stop condition: `onfail:stop` (default) halts the cycle clean on the default branch; `onfail:skip` parks the failed issue via the `/iflow-pause` conventions and continues. `issue-flow status` (and `/iflow-status`) now report an in-flight cycle (`cycle_active`) when the state file is present.
- **Epic awareness in `/iflow-pick` + cleanup stage gate (#139).** Stage 2 of the staged-planning epic (#144) closes the navigation loop. `/iflow-pick` now sources an **active epic's current-stage unblocked issues** as a candidate tier (between parked work and the general GitHub list), using `issue-flow agent epic-status <N> --json`'s `next_candidates` as the fast path, so an epic advances stage by stage instead of stalling. `/iflow-cleanup` gains an **epic stage gate**: when the just-merged issue was the last open one in its stage (detected via a `- Published: #<N>` line in an `epic<M>_plan.md` and confirmed with `agent epic-status`), it **offers** — never automatically — to post a stage-summary comment on the anchor issue and run `/iflow-epic <M> publish` for the next stage. Publishing and commenting stay the user's explicit call.
- **Developer docs: dedupe mode section in developing.md (#153).** Replace duplicated user-facing "Scaffolding modes" content with a slim "Working on scaffolding modes" contributor section pointing to configuration.md; keep modes.toml/modes.py and template-gating notes for package maintainers.
- **Documentation site logo (#151).** Wire the logo into the Zensical docs theme via `zensical.toml`; the header uses `docs/static/images/logo-light-right-color.svg` (SVG variants also committed under `docs/static/images/`).
- **New `/iflow-cycle` surface — hands-off batch processing (#141).** First runnable slice of the cycling-mode epic (#145): `/iflow-cycle <queue-spec>` (skill + command twin, standard mode only, off-path) processes **many issues in a row** under a single up-front confirmation — the batch equivalent of `/iflow-yolo`. It resolves the queue via `issue-flow agent queue` (explicit numbers, `label:<L>`, or `epic <N> [stage <k>]`), then runs each issue through the yolo chain **verbatim** (every safeguard stays a stop condition, never a skipped guard). A documented **strictly-necessary-input rule** limits interruptions to unfixable failures, refused merges / non-fast-forward pulls, ambiguous or not-actually-small specs, and anything outside the confirmed queue; the default failure policy **stops the whole cycle** on the first such condition and leaves the repo clean on the default branch. A safety cap (10) guards against runaway unattended runs.
- **Restore lost epic-skill template changes from the #147/#148 stacked squash-merge.** The GitHub squash-merges of the stacked epic PRs dropped #137's and #138's edits to the `iflow-epic` skill/command templates (the `## Action: publish` section and the `agent epic-status` CLI fast-path note): those squash commits captured only the tracking `.md` files, computing their diffs against a base where the code already appeared applied. This restores the template edits (and the reworked contract tests) so the shipped `/iflow-epic` skill matches its already-merged CLI (`agent epic-status`) and its changelog entries.
- **New `issue-flow agent queue` command (#140).** The deterministic groundwork for cycling mode (epic #145): a new `queueplan` module parses `Depends on #N` / `Blocked by #N` lines (marker lines only, so prose refs never create edges), Kahn-toposorts the queue with numeric tie-breaks for determinism, and flags `blocked` (open dependency outside the queue), `skipped_closed`, and `independent` (no dependency relation in either direction to any other member — the parallel-safe signal for a later stage); dependency cycles are reported and never silently broken. `agent queue [N ...] [--label L] [--epic N] [--json]` resolves exactly one source (the `--epic` source reuses the `epicplan` parser and the current stage's published specs), refuses a partial fetch on the explicit-numbers source so a typo never shrinks the queue, and adds `gitutils.gh_issue_meta()` / `gh_issue_list_meta()`. Read-only — nothing is executed. `/iflow-cycle` (#141) consumes this.
- **New `issue-flow agent epic-status` command (#138).** The deterministic half of epic navigation: a new `epicplan` module parses `epic<N>_plan.md` (the contract `/iflow-epic` writes — stages, `### Issue:` specs, `Depends on:` / `yolo:` / `Published: #<M>` lines, placeholders folded onto published numbers, `## Later` ignored), and `agent epic-status <N> [--local] [--json]` cross-references published issue states via a new `gitutils.gh_issue_state()`: stages with per-issue state (`unpublished`/`open`/`closed`/`unknown`) and blockers, the current stage, and the next open, unblocked candidates. Read-only; a missing `gh` degrades to `unknown` states instead of failing. The epic skill and command offer it as their CLI fast path.
- **Epic publishing (#137).** `/iflow-epic <N> publish [stage <k>]` turns a `Status: confirmed` epic plan into real GitHub issues, stage by stage: dry-run listing, then one consolidated confirm, then `gh issue create` per unpublished spec in dependency order (yolo label applied only when the recorded judgment says yes *and* the label exists; `stage <j> issue <k>` placeholders resolved to real numbers where published), `- Published: #<M>` recorded back into the plan (idempotent re-runs skip published specs), and a `- [ ] #<M>` task list appended to the anchor issue (append/patch only — user body text is never rewritten). Drafting remains write-free on GitHub.
- **New `/iflow-epic` surface + `05-epics/` scaffold, draft-only (#136).** First slice of the staged-planning epic (#144): planning a change too large for one issue now has a home. `/iflow-epic <N>` (skill + command twin, standard mode only, off-path) drafts `.issueflows/05-epics/epic<N>_plan.md` anchored to GitHub issue `<N>`: Goal / Constraints / sequential stages, each stage holding manageable issue specs (self-contained spec paragraph, explicit `Depends on:` lines with `stage <j> issue <k>` placeholders for unpublished issues, and a per-issue yolo-fitness judgment), with sizing rules (one issue = one branch = one PR) and stage discipline (detail 2–3 stages, sketch the rest). Strictly **draft-only**: publishing the confirmed plan to GitHub issues is the next slice (#137). `init`/`update` now create the `05-epics/` folder; the dispatcher and rules enumerate the new surface as off-path.

## [0.4.3] - 2026-07-10

- **New `issue-flow agent version-plan` command (#133).** The deterministic fast path for the release-strategy work in #125: detects the strategy from `pyproject.toml` (static `[project] version` → uv; `dynamic = ["version"]` + setuptools-scm/hatch-vcs/versioningit → git tag), reads the current version (static field or latest reachable tag via new `gitutils.latest_tag()`), and applies the PEP 440 bump arithmetic in the new `versionplan` module (same level table and pre-release-aware default as the skill; combined levels in canonical order; forward-only pre-release channels; tag style preserved). Read-only by design — it prints the exact commands (`uv version --bump …`, or `git tag` / `gh release create` for tag projects, flagged "after the PR merges") and never edits files or creates tags. The `iflow-version-bump` skill offers it as its CLI fast path; a filled `this-project.md` release section is reported (`brief_release_section`) and still wins over detection.
- **Release-strategy-aware version bump (#125).** `iflow-version-bump` no longer assumes a static `[project] version`: it resolves the project's **release strategy** first — the new "Release & version bump" section of `this-project.md` (user-owned, always wins), else detection from `pyproject.toml` (`dynamic = ["version"]` + setuptools-scm/hatch-vcs/versioningit → **git-tag derived**; static version → the unchanged uv path). For tag-derived projects the bump becomes a **planned tag** computed from the latest tag with the same level table: `/iflow-close` edits nothing, promotes the changelog with the planned version, and the tag is created **after the merge** (via `/iflow-cleanup`'s consolidated confirm, or the yolo close's post-merge step) — never on the issue branch, where a squash merge would orphan it. The skill also records a discovered/clarified strategy back into `this-project.md` so it is only rediscovered once; new starter briefs ship the section pre-scaffolded.

## [0.4.2] - 2026-07-10

- **Workspace registry with default repo (#126).** Multi-repo workspaces can now declare a **default ("parent") member** in a workspace-root `issueflow-workspace.toml`, created with the new `issue-flow workspace init [--default <member>]` command (members auto-discovered; a default that is not a scaffolded member is refused). `issue-flow agent resolve` reports the workspace context (`workspace_root`, `workspace_default`, `workspace_members`) and, when no scaffold is found walking up, falls back to the default member (`resolved_via_workspace_default: true`) — replacing only the final "stop and ask" step; explicit `root:`/`repo:` hints, the nearest scaffold, and the branch heuristic all still win. Scaffolded resolution contracts and the multi-repo design doc are updated; a single shared `.issueflows/` folder stays deliberately unsupported (per-repo issue numbering, per-repo lifecycle, archive recovery via each repo's git history).

- **Test hardening: archive folder safety + template↔CLI consistency.** A regression test now pins `/iflow-archive`'s safety contract: `issue-flow agent archive` deletes only the chosen `issue<N>_*` groups inside `03-solved-issues/` — sibling folders (`00-tools/`, `04-designs-and-guides/`, `01-current-issues/`) survive untouched even when they contain issue-pattern filenames, and so does the dated summary file. New `tests/test_template_cli_consistency.py` parses every packaged template for `issue-flow agent <cmd>` and backticked `issue-flow <cmd>` references and asserts each is a real Typer command, so a renamed or removed CLI command can no longer leave scaffolded skills pointing at something that doesn't exist.
- **Documentation site (Zensical + Read the Docs).** The `docs/` pages are now a proper documentation site built with [Zensical](https://zensical.org) (config in `zensical.toml`, new landing page `docs/index.md`, changelog page embedding `HISTORY.md` via pymdownx snippets) and published on Read the Docs via `.readthedocs.yaml` (build.jobs recipe from the official RTD guide). Build locally with `uv run zensical build` / `serve`; zensical lives in a new `docs` dependency group.
- **New `issue-flow agent switchback` command.** The mechanical "switch back when safe" half of `/iflow-close` now has a deterministic CLI fast path: it refuses (exit 1, listing the dirty paths) while the working tree is dirty, otherwise runs `git switch <default>` followed by `git pull --ff-only`, surfacing (never forcing) a refused fast-forward. Backed by new `gitutils.dirty_paths()` / `switch_branch()` / `pull_ff_only()` helpers; the `iflow-close` skill and command templates prefer it and keep the manual steps as fallback. Branch deletion still belongs to `/iflow-cleanup`.
- **Python 3.11+ support.** `requires-python` relaxed from `>=3.13` to `>=3.11` (nothing in the codebase needs newer than `tomllib`); CI now tests 3.11 / 3.12 / 3.13. Development stays pinned to 3.13 via `.python-version`.
- **README slimmed down.** The deep-dive sections moved to `docs/cli.md`, `docs/configuration.md`, `docs/editors.md`, and `docs/graphify.md`; the README keeps the pitch, install, quick start, and a CLI overview. This also adds the previously missing **Skill levels** documentation (the old README linked to a `#skill-levels` section that didn't exist).
- **Repo hygiene.** `graphify-out/graph.html` and `graphify-out/graph.json` (multi-MB, fully regenerated on every graphify run) are no longer tracked in git; `GRAPH_REPORT.md` stays tracked because the scaffolded skills read it.
- **Slash-less iflow chat invocation (#118).** Users can type `iflow plan`, `iflow pick`, and other lifecycle commands in chat (space-separated) when `/` and `@` are awkward on their keyboard; always-on rules map chat aliases to lifecycle skills. Hyphen (`iflow-plan`) and slash (`/iflow-plan`) forms remain supported. Lifecycle skill templates and `docs/issue-workflow.md` document the space form first.
- **Multi-root workspace support, Phase 1 (#67).** New `issue-flow agent resolve` discovers the project root, explicit `owner/repo`, branch context, and sibling scaffolds; lifecycle skills/commands include a shared resolution contract (`git -C`, always `gh --repo`). Cursor `issueflow-rules.mdc` is path-scoped (`alwaysApply: false`, `globs: ["**/*"]`) so sibling repos in one editor workspace no longer merge always-on rules. Adds `src/issue_flow/project.py`, design doc `multi-repo-workspaces.md`, and README/workflow guidance. Workspace registry, cross-repo linked issues, and multi-repo status dashboard deferred to follow-ups.
- **Step model directives (#113).** Lifecycle skills and command twins now carry an advisory `### MODEL & EXECUTION DIRECTIVE` section (`economy` vs `reasoning`) baked at `issue-flow update`. Packaged defaults live in `step_profiles.toml`; projects override per stem via `[issueflow.step_profiles]` and toggle with `step_directives`, `model_label_flows`, `deep_model_label`, and `fast_model_label` under `[issueflow]` (with env fallbacks). `/iflow-pick` can announce label-based session profile hints when `model_label_flows` is enabled.
- **Iterative `/iflow-fix` polish (#114).** `/iflow-start` and `/iflow-close` (plus the advanced `python-quality-tools.md` design doc) now nudge agents to run `ruff check --fix` and `ruff format` when ruff is already in the project. README also documents `/iflow-archive` and `issue-flow agent archive` (#84).
- Added a README Acknowledgements row crediting [mattpocock/skills](https://github.com/mattpocock/skills) as the source of the bundled `grill-me` Agent Skill. (#108)
- Align issues with plan. (#85)
- **Label-driven yolo flow (#106).** Issue labels can now select the flow: when `/iflow-pick` picks an issue carrying the (configurable) yolo label, it routes it through `/iflow-yolo` with one combined confirmation. Controlled by two new `[issueflow]` keys in `.issueflows/config.toml` — `label_flows` (default `true`) and `yolo_label` (default `"yolo"`), with `ISSUEFLOW_LABEL_FLOWS` / `ISSUEFLOW_YOLO_LABEL` env fallbacks; `issue-flow config add` now writes all six keys. The yolo chain also closes the loop: a new `yolo` token on `/iflow-close` writes the changelog bullet without a confirm prompt, merges the PR via `gh pr merge --squash` (`--squash --auto` fallback when blocked), then switches back to the default branch and pulls. Branch deletion still belongs to `/iflow-cleanup`.
- **New `--version` flag (#104).** `issue-flow --version` prints the installed package version (read from package metadata) and exits, implemented as an eager option on the root Typer callback. Landed via an interactive `/iflow-fix` session.
- **New `/iflow-archive` command + `agent archive` CLI (#84).** A new off-path, destructive-but-gated workflow surface (command + matching `iflow-archive` skill, included in both the `standard` and `simple` modes) that shrinks a grown `.issueflows/03-solved-issues/` folder: selected `issue<N>_*` groups are summarised into a single dated `YYYY-MM-DD_archived_issues.md` file — whose header records the pre-archive git ref so every original stays recoverable via `git show <ref>:<path>` — and the original files are then deleted. The flow requires a clean working tree, defaults to keeping the 5 most recent solved groups (`keep <K>`, an explicit number list, or `all` override), and deletes nothing before one consolidated confirmation; `/iflow` never auto-dispatches to it. The mechanical deletion has an optional CLI fast path, `issue-flow agent archive <N> ... [--dry-run] [--json]` (backed by `tracking.plan_archive`/`apply_archive` and a new `gitutils.head_sha()`), which refuses the whole run when any requested issue has no solved group; the per-issue summaries stay agent-side per the agentic-CLI design constraints.

## [0.4.1b3] - 2026-06-28

- **New `issue-flow config add` command (#96).** Adds a `config` CLI sub-app whose `add` command materializes `.issueflows/config.toml` on demand instead of relying on `init --mode` to create it. It writes the three keys issue-flow actually reads from `config.toml` — `mode`, `caveman_default`, `grill_me_default` — seeding each from its `ISSUEFLOW_*` env var / `.env` when set, otherwise the issue-flow default (`standard`, `false`, `false`), into a commented `[issueflow]` table, then prints a short guide for hand-editing it later. The other `ISSUEFLOW_*` settings are environment-only and are deliberately not written there (they would have no effect in `config.toml`). An existing file is left untouched unless `--force`, which upserts the three keys via `tomlkit` while preserving user comments and `[modes.*]` tables; `--json` emits a machine-readable result. Backed by `modes.write_default_config()` and `Settings.seed_config_values()`, documented in the README Configuration section.

## [0.4.1b2] - 2026-06-28

- **New optional `grill-me` planning skill (#32).** `issue-flow init` now scaffolds a `grill-me` Agent Skill — a relentless planning interview adapted from [mattpocock/skills](https://github.com/mattpocock/skills) and tuned to the issue-flow workflow (one question at a time, each with a recommended answer; explore the code/issue instead of asking when answerable; fold the resolved decisions into `issue<N>_plan.md`). Like `caveman` it ships in the `standard` mode (the `simple` mode omits it) and is model-invocable, so it stays dormant until you ask for it ("grill me") and turns off via "stop grilling" / "normal mode". A new opt-in `[issueflow].grill_me_default` key in `.issueflows/config.toml` (default `false`, with an `ISSUEFLOW_GRILL_ME_DEFAULT` env fallback; the persisted value wins so a stray env can't flip it on `update`) makes grilling on by default during planning: when enabled — and the `grill_me` skill is in the active mode — `init` / `update` render an always-on grill-me pointer into the managed rule body (`templates/rules/_body.md.j2`) and a grilling step into the `/iflow-plan` skill. Backed by `modes.read_grill_me_default()` and `Settings.resolve_grill_me_default()` (resolution order `config.toml` > env > `false`), a new `grill_me_default` template-context key, and a commented `ISSUEFLOW_GRILL_ME_DEFAULT` hint in the starter `.env`; documented in the README (Modes note + config table) and a new grill-me design guide.
- **New optional `caveman` Agent Skill (#81).** `issue-flow init` now scaffolds a `caveman` skill — a terse, token-greedy response style adapted from [JuliusBrussee/caveman](https://github.com/JuliusBrussee/caveman) (full intensity only, English only) — as part of the `standard` mode (the `simple` mode omits it). It is model-invocable, so it stays dormant until you ask for it ("caveman" / "token greedy") and turns off via "stop caveman" / "normal mode"; it is registered as a membership-gated pointer in the `AGENTS.md`/rules managed block (never the always-on ruleset). Also adds a README **Acknowledgements** table crediting upstream projects (caveman, graphify, and the core runtime libraries) and drops the unused `openai` dependency.
- **`/iflow-close` now returns to the default branch when clean (#82).** After opening or updating the PR, `/iflow-close` switches back to the detected default branch when the working tree is clean; pass `stay`, `stay on branch`, `don't switch`, or `dont switch to main` to remain on the issue branch. `/iflow-cleanup` still owns post-merge branch deletion.
- **Cursor scaffolding is now skills-first (#79).** Cursor output uses Agent Skills as the primary slash-menu surface (`.cursor/skills/`) while preserving the always-on `.mdc` rule; generated `.cursor/commands/` files are pruned on update, unrelated user commands are preserved, and the dispatcher skill now lives at `iflow` instead of `iflow-iflow`.
- **BREAKING: Renamed all slash commands from `/issue-*` to `/iflow-*` (#71).** The entire command family is now consistent with the `/iflow` dispatcher as the namespace root: `/issue-pick` → `/iflow-pick`, `/issue-init` → `/iflow-init`, `/issue-plan` → `/iflow-plan`, `/issue-start` → `/iflow-start`, `/issue-pause` → `/iflow-pause`, `/issue-close` → `/iflow-close`, `/issue-cleanup` → `/iflow-cleanup`, `/issue-yolo` → `/iflow-yolo`, `/issue-fix` → `/iflow-fix`, `/issue-status` → `/iflow-status`, `/graphify` → `/iflow-graphify`. Skills renamed from `issueflow-issue-*` to `iflow-*` (removing redundancy), `issueflow-version-bump` → `iflow-version-bump`, `issueflow-history-update` → `iflow-history-update`, `issueflow-graphify` → `iflow-graphify`. Run `issue-flow update` to migrate existing projects; old command files and skill folders are automatically pruned with a summary message.
- **New `/iflow-status` overview command (#20).** A read-only, off-path command (plus matching `iflow-status` skill) that prints a snapshot of where every issue stands: the local tracking state under `.issueflows/` (focus issue with its lifecycle stage via the `/iflow` logic, parked work, solved archive) plus open GitHub issues cross-referenced against the local folders and tagged focus / parked / solved-locally / untracked.
