# Issue #404: Replace [Unreleased] edits with commit trailers and a release-time HISTORY rebuild

Source: https://github.com/jepegit/issue-flow/issues/404

## Original issue text

## Problem

Feature PRs all insert changelog bullets under the same `## [Unreleased]` lines in `HISTORY.md`. After one of those PRs is squash-merged, the next open PR conflicts on those lines. GitHub's merge button does not run issue-flow's keep-both resolver, so the conflict lands on the person merging.

This showed up on cellpy while closing a series of small docs PRs (jepegit/cellpy#1023, merged as #1166, #1167, and #1168, plus #1158). Each close appended one bullet under `[Unreleased]`. The next branch then conflicted.

## Already shipped, and why it is not enough

- #240 (closed) taught `sync-branch` to keep both `[Unreleased]` bullets. That runs locally, on the branch being closed. It does not run when someone presses Merge on GitHub, and it does not help a second PR that was opened earlier.
- #260 (open) adds `/iflow-pr-sync` to refresh a queue of PRs that went `DIRTY`, usually because of `HISTORY.md`. That repairs the queue after the fact. It is still manual, and it still leaves every feature PR editing the same lines. Leave #260 open for that repair path.
- #288 (closed) added `defer_changelog`: `apply-changelog` can write the bullet onto the default branch after merge, from a `### Deferred changelog` block in the status file. Close still commits `HISTORY.md` on the feature branch today, so the conflict source remains.

This is a follow-up, not a duplicate of those three. `pr-sync` and `defer_changelog` do not stop feature PRs from editing the same lines. The change here removes the shared `[Unreleased]` section so changelog text no longer needs that repair.

## Proposal

Stop editing `HISTORY.md` on feature PRs. Close writes the note into the commit message. `HISTORY.md` is rebuilt only when a version is cut, by prepending one new version section. Older sections are never rewritten.

### Trailers

Close generates these trailers. A person does not type the id.


Changelog: <bullet text> (#N)
Changelog-Date: YYYY-MM-DD
Changelog-Id: <short id>

- `Changelog` is the bullet sentence, including the issue reference the project already uses.
- `Changelog-Date` is a human sort key inside the release being cut. It does not file the note into an older version section.
- `Changelog-Id` is a short id (ULID or 12 hex), one per bullet, generated by close. The same issue can have many bullets (cellpy #1023 had three). The same id with newer text replaces the older text. A new id is a new bullet. Identical ids inside one squash body collapse to one bullet.

The issue number is not unique enough to be the id. The commit SHA dies on squash, so it cannot be the id either.

### No `[Unreleased]` section

`HISTORY.md` contains only released version sections (`## [version] - date`). There is no `## [Unreleased]` heading to conflict on.

`issue-flow changelog list` prints the unreleased notes at any time and does not write the file. The scan window is commits after the commit that wrote the previous version section, minus any `Changelog-Id` already recorded in `HISTORY.md`. The same id, newest text wins.

`issue-flow changelog release <version>` prepends `## [<version>] - <date>` from that same list, then stores the shipped ids in an HTML comment in that version section so a later list does not print them again. It refuses when:

- the version heading already exists
- the working tree is dirty
- the command is not run on the default branch
- `HEAD` moved under a concurrent release
- the list is empty (no empty version heading)

It never rewrites older sections.

The first release after adoption folds the bullets already under `## [Unreleased]` into the new version section, then deletes that heading. After that, the heading stays gone.

### Manual edits

- Rewording or deleting text inside a shipped version section sticks. Release does not regenerate that section.
- A bullet dropped at release does not come back, because its commit is behind the release commit. Restore it with a new id.
- A bullet typed by hand into `HISTORY.md` between releases is invisible to `changelog list` and will not be moved. New notes are trailers, or a `changelog add` helper that creates the trailer without editing `HISTORY.md`.

### CI, close, and squash

Close does not touch `HISTORY.md`. CI rejects a feature-PR diff of `HISTORY.md` unless the commit is a release.

The squash commit message must keep the individual commit bodies, so the trailers survive. cellpy's squash template does this. A "PR title only" template drops them. `changelog list` and `changelog release` read the squash message on the default branch.

A cherry-pick onto a line whose `HISTORY.md` does not contain that id (a v1.x backport, for example) lists the note again. That is intended.

## Out of scope

- Changing a repo's squash-merge policy.
- Auto-merging.
- Resolving conflicts that are not `HISTORY.md`.
- Implementing the reader inside cellpy. cellpy would adopt this after issue-flow ships it.

## Acceptance

- `changelog list` prints unreleased trailers and does not write the file.
- `changelog release <version>` prepends one version section and records the shipped ids.
- The same id with newer text replaces; a repeated id inside one squash body collapses; a new id is a new bullet.
- Release refuses to rewrite an older section, to repeat a version heading, to run on a dirty tree, or to write an empty heading.
- A feature close does not diff `HISTORY.md`.
- Tests cover the scan window, id replace/collapse, and the refuse cases.
- Docs sit next to the existing changelog-conflicts guidance, including a migration note for a repo that still has an `[Unreleased]` section.
